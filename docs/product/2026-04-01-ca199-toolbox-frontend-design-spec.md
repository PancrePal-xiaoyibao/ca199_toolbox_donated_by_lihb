# CA199 Toolbox 前端设计与开发规范

- 日期：2026-04-01
- 项目：CA199 医疗指标可视化工具
- 文档类型：前端设计规范 / 开发提示词
- 适用阶段：新版产品重构前期

## 1. 文档目标

本文档用于明确新版前端的：

1. 产品交互形态
2. 前端技术栈
3. 页面信息架构
4. 视觉与样式规则
5. 组件拆分方式
6. AI 前端开发提示词

目标不是单纯“做漂亮”，而是做出一个：

`适合门诊展示、适合患者维护、具备专业感、且便于 AI 协作开发`

的前端系统。

## 2. 前端形态结论

首版前端推荐形态：

`本地优先的 Web 应用`

而不是：

- 原生 App 优先
- 单文件 HTML 长期堆叠
- 医生端后台系统

推荐原因：

1. 适合平板横屏展示
2. 适合手机纵向查看
3. 适合本地文件导入
4. 适合后续接 Python 解析/OCR
5. 适合未来演进到小程序或桌面壳
6. 适合 AI 辅助持续重构

## 3. 前端产品交互模型

新版前端采用三 Tab 结构：

- `病程总览`
- `病情详情`
- `病程摘要`

### 3.1 病程总览

定位：

- 默认首页
- 医生主视图
- 平板现场展示的核心页面

交互要求：

1. 导入数据后自动生成默认视图
2. 不把“生成图表”作为首要交互
3. 默认展示单核心指标大图
4. 治疗时间轴与关键事件和主图严格对齐
5. 支持最近 3 个月、6 个月、12 个月、全部等快捷切换
6. 支持截图模式

### 3.2 病情详情

定位：

- 深入查看层
- 复杂病程和多指标分析层

交互要求：

1. 支持 2 至 3 个核心指标同屏对照
2. 支持更多实验室指标按分类展开
3. 支持显示明细数据、备注、阶段性治疗信息
4. 支持筛选，但筛选不是视觉中心

### 3.3 病程摘要

定位：

- 患者视角的纵向病程记录
- 面向回顾和沟通

交互要求：

1. 用时间轴纵向列出病情经过
2. 每个节点展示时间、事件类型、简述、补充记录、下一步安排
3. 支持用户补充患者语言
4. 适配手机阅读

## 4. 前端技术栈建议

推荐技术栈如下：

### 核心框架

- `React`
- `TypeScript`
- `Vite`

原因：

1. 开发效率高
2. AI 生成质量稳定
3. 组件化清晰
4. 适合后续持续迭代

### 样式方案

推荐二选一：

- `Tailwind CSS`
- `CSS Modules`

建议优先：

`Tailwind CSS + 局部 CSS 变量`

原因：

1. 适合快速原型和高频迭代
2. 便于 AI 输出一致的布局代码
3. 可以用 CSS 变量统一主题风格

### 数据可视化

- `ECharts` 负责主图和对照图
- `SVG + React` 负责病程时间轴、事件轨、摘要时间轴
- 必要时使用少量 `d3-scale`

原因：

1. 当前项目已有 ECharts 使用经验
2. 趋势图交互成熟
3. 时间轴结构用组件化 SVG 更可控

### 状态管理

- `Zustand`

原因：

1. 比 Redux 更轻
2. 学习成本低
3. 适合本地数据驱动应用

### 本地存储

- `IndexedDB`
- 可配合 `idb`

原因：

1. 比 localStorage 更适合结构化数据
2. 更适合病程记录、导入缓存和用户补充内容

### 文件与时间处理

- `PapaParse` 处理 CSV
- `dayjs` 处理日期

### 动画

- 优先 `CSS`
- 必要时使用 `Framer Motion`

原则：

- 只做少量有意义的过渡
- 不做花哨干扰型动效

## 6. 页面布局规则

## 6.1 全局布局

全局布局应满足：

1. 平板横屏优先
2. 手机纵向不崩
3. 大屏时主图占主要视觉中心
4. 控件区弱化，不抢图表注意力

推荐结构：

- 顶部：患者基础信息 + Tab
- 中部：当前页面核心内容
- 底部：低频入口与辅助信息

## 6.2 病程总览布局

推荐采用：

- 顶部：患者头部信息
- 主区左/上：核心指标主图
- 主区右/下：治疗时间轴与关键事件
- 下方：状态摘要卡片

屏幕足够宽时：

- 主图和信息卡并置

屏幕较窄时：

- 主图优先，时间轴与卡片纵向堆叠

## 6.3 病情详情布局

推荐采用模块化展开：

- 顶部：筛选条
- 中部：多指标图表
- 下部：数据明细

重点：

- 详情页也要整洁，不做后台表格堆满屏

## 6.4 病程摘要布局

推荐采用：

- 顶部：阶段筛选 / 时间范围
- 主体：纵向时间轴
- 节点卡片：精简、清楚、可补充

## 7. 视觉设计方向

整体视觉方向：

`专业、冷静、可信、信息编辑化`

不是：

- SaaS 仪表盘
- 土味工具页
- 花哨健康 App

### 7.1 视觉关键词

- 临床信息感
- 编辑式版面
- 清晰层级
- 克制配色
- 强时间秩序

### 7.2 色彩规则

建议采用中性色为主，语义色为辅。

建议语义分工：

- 主文本：深灰黑
- 次文本：中灰
- 背景：暖白或冷白
- 治疗：偏蓝或墨青
- 检查事件：偏绿
- 异常值 / 风险：偏红
- 患者记录：偏棕灰或低饱和暖色

禁止：

- 紫色主色方案
- 彩虹式杂色图表
- 高饱和大片撞色

### 7.3 字体规则

避免：

- Inter
- Roboto
- Arial
- 单纯系统默认堆栈审美

推荐方向：

- 标题字体有一定识别度，但不过分装饰
- 正文字体以中文阅读舒适为优先

建议：

- 中文正文可考虑 `Noto Serif SC` / `Source Han Serif SC` 风格方向
- 英文和数字可搭配更克制的无衬线

原则：

- 标题有气质
- 正文高可读
- 数据数字稳定清晰

### 7.4 卡片与边框

建议：

- 少量卡片
- 更强调版面分区而不是圆角盒子堆叠
- 使用细边线、留白、轻阴影控制层级

不要：

- 大量圆角卡片堆满页面
- 过厚投影
- 强烈拟物效果

## 8. 前端交互规则

以下规则应写入开发要求：

1. 首页不出现“生成图表”主按钮
2. 数据导入后自动进入默认视图
3. 首页默认只显示一个核心指标
4. 多指标对照只放到详情页
5. 时间范围切换采用快捷选项
6. 筛选器默认折叠或弱化
7. 截图模式可隐藏低价值控件
8. 颜色只表达语义，不承担装饰任务
9. 事件点击后可联动高亮图表位置
10. 关键文本必须适合医生快速扫读

## 9. 状态设计建议

建议前端按以下状态分层：

### 9.1 应用级状态

- 当前 Tab
- 当前患者数据集
- 当前时间范围
- 当前截图模式开关

### 9.2 图表状态

- 当前核心指标
- 当前选中的事件
- 图表缩放范围

### 9.3 病程摘要状态

- 时间轴节点列表
- 用户补充记录
- 自动提取节点

### 9.4 导入状态

- 文件加载中
- 文件解析结果
- 字段映射
- 错误提示

## 10. 前端 AI 开发提示词

下面这段可直接给 AI 前端开发工具使用。

```text
你是一个资深医疗信息产品前端设计师和工程师。请为一个“本地优先的病情整理与就医展示工具”设计并实现高保真前端界面。

产品目标：
1. 家属在门诊现场用平板横屏向医生展示病情
2. 医生在 10 秒内看懂核心指标趋势、治疗过程和关键事件
3. 患者可在手机上查看和补充病程摘要
4. 所有数据本地加载，不强调云端协作

用户角色：
- 家属：主要操作者
- 患者：查看和补充记录
- 医生：主要浏览者

信息架构：
- 病程总览
- 病情详情
- 病程摘要

页面规则：
1. 默认进入“病程总览”
2. 病程总览必须打开即读，不依赖复杂配置
3. 顶部为三 Tab 导航，清晰但不过度占空间
4. 病程总览以“单核心指标大图”为中心
5. 治疗时间轴和关键事件必须与主图时间轴严格对齐
6. 病情详情支持 2-3 个核心指标同屏对照
7. 病程摘要使用纵向时间轴，展示检查、治疗、医生意见、患者记录、下一步安排
8. 页面优先适配平板横屏，同时兼顾手机纵向阅读
9. 风格要专业、冷静、可信，避免像后台系统、表单工具或土味数据页
10. 不要使用紫色渐变白底、Inter、Roboto、系统默认审美
11. 减少按钮感和配置感，让界面像“病情总览”而不是“图表生成器”
12. 支持截图友好的模式

技术要求：
- React + TypeScript
- Vite
- ECharts
- Tailwind CSS
- Zustand
- 组件化实现
- 响应式布局
- 不要把所有逻辑写在一个文件里

请输出：
1. 页面结构说明
2. 组件拆分方案
3. 状态设计
4. 样式设计原则
5. 可直接运行的前端代码

当前页面存在的问题：
- 工具感太强
- 默认需要用户先选择和生成
- 信息层级不清
- 视觉风格偏土
- 治疗和事件没有形成强组织关系

请在保留“本地安全、模板清楚、医生一目了然”这些优点的前提下重构界面。
```

## 11. 负面约束提示词

为了避免 AI 生成通用烂样式，可追加以下约束：

```text
禁止事项：
- 不要做成管理后台风格
- 不要默认展示大量输入框和按钮
- 不要把筛选器放在视觉中心
- 不要使用紫色主色、默认圆角卡片堆叠、常见 SaaS 仪表盘布局
- 不要把 AI 助手放进医生主视图
- 不要把全部指标默认摊开
- 不要把时间轴做成附属小部件，必须是核心结构的一部分
```

## 12. 开发阶段建议

前端开发建议分三步：

### 第一阶段：静态重构

- 搭建 React 工程
- 固定三 Tab 布局
- 完成高保真静态界面
- 用 mock 数据验证信息层级

### 第二阶段：数据接入

- 接入现有 CSV
- 接入本地缓存
- 建立图表和时间轴联动

### 第三阶段：录入增强

- 接入患者补充记录
- 接入摘要节点生成
- 为后续 OCR / Python 解析预留接口

## 13. 结论

这个项目的前端不应继续沿用“单 HTML + 控件驱动”的旧模式，而应升级为：

`本地优先的 React 前端应用`

核心思路不是做成复杂系统，而是：

- 首页更像病情总览
- 详情页更像证据展开
- 摘要页更像病程记录

这套结构既适合当前真实使用场景，也最适合 AI 时代的持续协作开发。
