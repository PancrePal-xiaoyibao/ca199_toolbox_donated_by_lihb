# CA199 Toolbox 新版产品设计文档

- 日期：2026-03-31
- 项目：CA199 医疗指标可视化工具
- 文档类型：产品设计文档
- 当前阶段：方案确认稿

## 1. 背景

当前 `ca199_toolbox` 的价值已经很明确：

1. 本地加载，数据不上传，安全边界清楚。
2. 模板简单，患者和家属容易上手。
3. 内容聚焦，医生在门诊中能较快抓住病情重点。

但当前版本也存在明显问题：

1. 视觉表达偏工具化，第一印象不够专业。
2. 主流程仍然是“加载文件 -> 勾选指标 -> 生成图表”，不够接近真实就医展示场景。
3. 信息层级不足，核心趋势、治疗过程、关键事件还没有形成一套清楚的阅读顺序。
4. 对复杂病程的承载能力有限，无法充分吸收高信息密度时间轴产品的优点。

参考对象带来的启发是：

- 参考 A 的优势是信息源强、时间轴组织能力强、病程视角完整。
- 当前版本 B 的优势是一目了然、本地安全、对无技术能力患者友好。

新版目标不是复制 A，也不是仅做美化，而是形成：

`B 的易读性 + A 的病程组织能力`

## 2. 产品定位

这是一个 `本地优先、门诊展示优先、患者可维护` 的病情可视化工具。

核心定位：

- 帮助家属在复诊现场用平板向医生快速展示病情重点。
- 帮助患者用手机查看或截图转发关键病程内容。
- 不替代医生判断，只负责让病情信息更清楚、更有顺序地被看到。

## 3. 核心用户与场景

### 3.1 核心用户

1. 家属：门诊现场的主要操作者。
2. 患者：手机查看、截图转发、补充病程记录。
3. 医生：主要浏览者，不承担录入责任。

### 3.2 核心场景

#### 场景 A：门诊/复诊现场

- 家属使用平板横屏展示页面。
- 医生在很短时间内查看核心指标趋势、当前治疗线和关键事件。
- 页面应默认可读，尽量减少额外操作。

#### 场景 B：患者手机快速转发

- 患者或家属在手机上查看病情核心内容。
- 可以截图或展示单屏摘要内容给其他医生、家人或病友。

#### 场景 C：病程回顾与补充

- 患者或家属在非门诊场景下补充关键病程节点。
- 逐步形成完整、可回看的病程记录。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 让医生第一眼看到核心指标趋势。
2. 让医生第二眼看懂治疗过程与指标变化的对应关系。
3. 让医生第三眼快速定位关键检查、影像和复查事件。
4. 让患者和家属能够维护自己的病程记录，但不增加过高使用门槛。
5. 保持本地加载和数据安全作为核心卖点。

### 4.2 非目标

1. 不自动给医生输出诊断性结论。
2. 不让 AI 在医生主界面中替代专业判断。
3. 首版不做实时语音助手。
4. 首版不以微信小程序作为主要交付形态。
5. 首版不追求覆盖所有医疗数据类型。

## 5. 设计原则

1. `医生先看懂，患者再理解`
2. `默认可读，交互只是增强`
3. `趋势优先，细节后置`
4. `同一份数据，多种表达`
5. `本地优先，安全边界清晰`
6. `页面像病情总览，不像配置工具`

## 6. 信息架构

新版采用三个一级 Tab：

- `病程总览`
- `病情详情`
- `病程摘要`

默认进入 `病程总览`。

这三个 Tab 不是三个独立产品，而是同一份病情数据的三种阅读模式。

### 6.1 病程总览

面向门诊展示，是默认首页，也是产品核心。

目标：

- 10 秒内让医生进入病情上下文。
- 默认呈现最重要的信息，不要求用户先做复杂配置。

默认信息层级：

1. 核心指标趋势
2. 当前治疗线与历史治疗
3. 关键事件节点
4. 当前状态卡片

### 6.2 病情详情

面向深入查看，承接更高密度的信息。

目标：

- 在不干扰首页清晰度的前提下，容纳复杂病程。
- 让懂数据、愿意深看的用户继续钻取。

典型内容：

- 2 至 3 个核心指标同屏对照
- 更多实验室指标分组查看
- 历史治疗展开
- 备注与原始记录入口
- 明细级时间点与异常值信息

### 6.3 病程摘要

面向患者视角的纵向病程时间轴。

目标：

- 用时间顺序讲清楚“发生过什么”。
- 帮助患者和家属回顾病情经过，也帮助医生快速补足背景。

内容结构：

- 就医节点
- 检查节点
- 治疗调整节点
- 医生意见
- 患者/家属记录
- 下一步安排

数据来源采用：

`自动生成骨架 + 手工补充`

即先从指标数据、用药数据和备注数据中提炼节点，再允许患者或家属补充人类可读的上下文。

## 7. 页面结构设计

## 7.1 病程总览页

推荐布局：平板横屏优先的单页总览。

页面结构：

1. 顶部：患者基础信息区
2. 主体上部：核心指标趋势主图
3. 主体中部：治疗时间轴 + 关键事件叠加
4. 主体下部：当前状态卡片 / 最近检查 / 快速摘要

### 主图策略

首版默认采用：

`单核心指标大图`

理由：

- 更符合医生第一眼阅读方式。
- 避免多指标同时出现带来的视觉竞争。
- 更适合门诊场景下快速说明问题。

同时保留切换能力：

- 可切换到其他核心指标
- 支持进入详情页查看多指标对照

### 病程总览页的关键交互

1. 默认打开即显示核心图，不再把“勾选指标 -> 生成图表”作为首要操作。
2. 治疗时间轴与事件节点和趋势图严格按时间对齐。
3. 点击关键事件时可以高亮对应时间点。
4. 支持快速切换时间范围，如最近 3 个月、6 个月、12 个月、全部。
5. 支持一键进入截图友好的展示状态。

## 7.2 病情详情页

推荐布局：模块化分组展开。

页面结构：

1. 顶部：筛选与时间范围
2. 中部：多指标对照区
3. 下部：详细记录列表、检查/备注/治疗明细

详情页重点不是“更多功能”，而是“更多证据”。

应该重点解决的问题：

1. 核心指标之间如何对照。
2. 治疗阶段如何与指标变化关联。
3. 哪些记录是重要节点，哪些只是补充数据。

## 7.3 病程摘要页

推荐布局：纵向时间轴。

每个节点建议包含以下字段：

- 时间
- 事件类型
- 标题
- 简述
- 数据依据
- 患者/家属补充
- 下一步安排

事件类型建议首版包含：

- 检查
- 治疗
- 复查
- 医生意见
- 患者记录
- 其他重要事项

这部分应尽量接近“病情经过日志”，而不是自动化总结卡片。

## 8. 数据模型建议

在现有 `data.csv`、`medication.csv`、`remarksline.csv` 基础上，建议未来补充一个可选的数据层：

- `summary_events.csv` 或本地结构化记录表

建议字段：

- `event_date`
- `event_type`
- `title`
- `description`
- `source`
- `doctor_note`
- `patient_note`
- `next_step`
- `importance`

其中：

- 现有数据文件继续承担“事实数据”的职责。
- 新增摘要事件层承担“叙事节点”的职责。

这样可以避免把趋势数据和病程叙事混在一起。

## 9. AI 使用边界

AI 可以帮助患者理解，但不应干扰医生判断。

因此建议明确分层：

### 9.1 医生主视图

- 不默认显示 AI 结论
- 不自动给出治疗建议
- 不输出带判断倾向的总结

### 9.2 患者辅助层

可以作为后续增强能力考虑：

1. 医学术语解释
2. 帮助整理病程摘要草稿
3. 帮助把零散备注整理成时间轴节点
4. 帮助患者理解数据变化的常见含义

所有 AI 内容必须明确标注：

`仅用于辅助理解，不替代医生意见`

## 10. 视觉方向

新版视觉不应停留在“本地 HTML 工具”的层级，而应更像一页专业病情总览。

视觉方向建议：

1. 专业、冷静、可信
2. 减少按钮感和表单感
3. 提高图表区权重，弱化配置区存在感
4. 让治疗线和事件线具有更强的秩序感
5. 平板横屏优先，同时兼顾手机单屏阅读和截图

应避免：

1. 过度装饰
2. 过多艳色
3. 默认展示过多控件
4. 像后台系统或数据开发工具

## 11. 版本规划

### v1：结构重构版

目标：

- 重构为 `病程总览 | 病情详情 | 病程摘要`
- 明确首页信息层级
- 重做首页视觉与布局
- 建立病程摘要时间轴
- 保持本地加载与离线能力

### v2：患者辅助增强版

目标：

- 引入患者友好的解释层
- 提供病程摘要草稿生成
- 优化手机端体验
- 增加更好的分享/截图能力

### v3：轻量小程序探索版

目标：

- 评估小程序是否适合承载患者记录与展示
- 保持数据导入与本地控制能力
- 严格控制隐私和数据边界

## 12. 首版范围与取舍

首版建议只做以下内容：

1. 新的信息架构
2. 新的病程总览主页面
3. 病情详情页基础能力
4. 病程摘要页基础时间轴
5. 截图友好的展示模式

首版不建议做：

1. 实时语音对话 AI
2. 医生结论自动生成
3. 高复杂度智能推荐
4. 小程序正式交付
5. 过度复杂的数据建模

## 13. 成功标准

如果新版设计有效，应能达到以下结果：

1. 家属在平板上打开后，无需复杂操作即可展示核心病情。
2. 医生能快速看懂核心指标趋势、治疗过程和关键事件。
3. 患者和家属能逐步沉淀更完整的病程摘要。
4. 产品既保持本地安全优势，又显著提升专业感和可读性。

## 14. 当前建议结论

新版不应只做视觉优化，而应完成一次明确的产品重构：

- 以 `病程总览` 作为医生现场展示的核心入口
- 以 `病情详情` 作为高密度信息承载层
- 以 `病程摘要` 作为患者视角的纵向病程记录层

这是当前项目最适合的演进方向，也是最能兼顾真实使用场景、数据安全和后续扩展性的方案。
