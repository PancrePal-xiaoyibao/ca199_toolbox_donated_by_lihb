# Case Organizer 患者向导页设计稿

- 日期：2026-04-01
- 项目：Case Organizer
- 文档类型：前端产品设计稿
- 当前阶段：方案确认稿

## 1. 页面定位

`患者向导页` 是 `case-organizer` 的患者入口页。

它的职责不是展示病情，而是帮助不会使用 CLI 或代码的患者、家属，通过一个本地 Web 页面完成以下流程：

1. 创建病例目录
2. 按模板放入资料
3. 检查资料是否齐全
4. 启动自动整理
5. 校对候选结果
6. 导出可用结果

它与 `ca199_toolbox` 的关系是：

- `case-organizer` 负责整理和结构化输入
- `ca199_toolbox` 负责病情展示与就医沟通

两者应保持同一设计体系，但不是同一页面。

## 2. 设计目标

页面目标：

1. 让不会命令行的患者也能完成病例整理
2. 让“建立目录树、分类放资料、启动处理”变成清晰流程
3. 降低用户把材料乱放、漏放、混放的概率
4. 让导出结果自然衔接到 `ca199_toolbox`

成功标准：

1. 用户不需要理解项目目录结构也能完成初始化
2. 用户能看懂应该把什么资料放到哪个分类
3. 用户能看到处理进度和失败项
4. 用户能在处理后完成最小校对
5. 用户能清楚找到最终输出位置

## 3. 与现有 UI 的关系

这部分和之前的 UI 设计应保持一致，但任务不同。

### 3.1 一致的部分

- 同样的视觉语言
- 同样的专业、冷静、可信风格
- 同样的中文医疗信息设计语气
- 同样的组件层级和留白原则

### 3.2 不同的部分

`case-organizer` 患者向导页：

- 是引导式任务页面
- 强调路径清晰
- 强调“下一步做什么”
- 强调目录模板和处理状态

`ca199_toolbox` 展示页：

- 是展示页面
- 强调一目了然
- 强调病情趋势、治疗与时间轴

结论：

`同一产品体系，不同任务入口`

## 4. 页面形态结论

首版采用：

`单页向导式流程`

不采用：

- 左侧目录树 + 右侧工作台
- 多页面跳转式后台系统
- 配置项很多的工具页

原因：

1. 患者和家属更容易理解
2. 适合把“整理流程”拆成连续步骤
3. 不会重新滑向“工具感太强”的界面

## 5. 页面主流程

页面采用六步主流程，顶部为总进度条，主体区域为当前步骤内容，底部为主要操作按钮。

流程如下：

1. `创建病例`
2. `放入资料`
3. `检查资料`
4. `开始整理`
5. `校对结果`
6. `导出结果`

## 6. 六步详细定义

### 6.1 第一步：创建病例

目标：

- 初始化标准病例目录

用户输入：

- 病例名称或患者代号

系统动作：

- 创建标准目录树
- 明确显示 `raw/`、`workspace/`、`exports/`

界面内容：

- 简短说明：这个页面会帮你建立一个标准病例目录
- 输入框：病例名称
- 目录预览卡片

输出结果：

- 标准目录树创建完成

### 6.2 第二步：放入资料

目标：

- 帮助患者按分类放入文件

系统约束：

- 患者只向 `raw/` 写文件
- 页面明确标识每个目录对应什么资料

推荐目录模板：

```text
raw/
  01_基本资料/
  02_诊断报告书/
  03_影像报告/
  04_病理与基因/
  05_检验检查/
    01_肿瘤标志物/
    02_血常规/
    03_肝肾功能/
    04_凝血/
    05_炎症指标/
    06_体液检查_尿便常规/
    07_其他检验/
  06_处方与用药/
  07_个人病情记录/
  08_手术与住院资料/
  99_待分类/
```

界面内容：

- 目录分类卡片
- 每类资料的例子说明
- 每类的文件数状态
- 可选上传入口：上传后直接写入当前分类目录

重点：

- `99_待分类` 必须保留
- 先让患者把材料放进去，不因不会分类而阻塞

### 6.3 第三步：检查资料

目标：

- 在真正处理前，先做一轮可读检查

界面内容：

- 已识别文件总数
- 各分类文件分布
- 未识别或不支持的文件
- 待分类文件
- 明显异常提醒

示例提醒：

- 没有任何诊断报告书
- 没有任何处方或用药记录
- 影像报告为空
- 某类文件格式不支持

这一页不做医学判断，只做资料检查。

### 6.4 第四步：开始整理

目标：

- 运行 `scan` 主流程

系统动作：

- 扫描 `<case>/raw`
- 对文件做本地直读或 MinerU 处理
- 写入 `<case>/workspace`

界面内容：

- 当前步骤说明
- 当前处理文件
- 成功数 / 失败数 / 待处理数
- 日志摘要

必要要求：

- 失败文件必须可见
- 失败原因必须可见
- 不允许静默失败

### 6.5 第五步：校对结果

目标：

- 对候选结果做最小人工校对

首版只做轻量校对，不做复杂编辑器。

界面内容：

- 核心诊断
- 治疗阶段
- 影像记录
- 检验与肿标
- 关键事件
- 来源文件追溯

交互原则：

- 先确认，再允许少量修改
- 不把页面做成复杂后台表格
- 每个信息块都能看到来源文件

### 6.6 第六步：导出结果

目标：

- 生成最终可用输出

输出目录：

```text
exports/
  normalized/
  legacy/
  printable/
  summaries/
```

导出内容：

- `normalized/`：标准 JSON/CSV，供 `ca199_toolbox` 使用
- `legacy/`：旧版 `ca199_toolbox` 的兼容文件
- `printable/`：病例摘要、后续 docx/pdf
- `summaries/`：患者或家属摘要

页面内容：

- 导出完成状态
- 输出路径
- 打开文件夹按钮
- 进入 `ca199_toolbox` 展示页的入口

## 7. 信息架构

页面分为三层：

### 7.1 顶部

- 页面标题
- 病例名称
- 六步进度条

### 7.2 中部

- 当前步骤主内容区

### 7.3 底部

- 上一步
- 下一步
- 当前主操作按钮

辅助信息如帮助说明、目录示例、失败文件列表可以在主区下方展开。

## 8. 视觉方向

视觉上应继承 `ca199_toolbox` 的整体风格，但更偏向“引导与确认”。

关键词：

- 专业
- 清楚
- 安心
- 低学习成本

避免：

- 像后台系统
- 像开发者工具
- 像表单堆砌页
- 过多配置项

视觉重点：

- 步骤感强
- 分类卡片清楚
- 目录结构不压人
- 处理状态和失败项显眼但不吓人

## 9. 与后端的接口关系

患者向导页首版不直接承载复杂业务逻辑，而是调用 `case-organizer` 已有能力：

- `init`：初始化病例目录树
- `scan`：扫描并生成 `workspace/`
- `review`：读取候选结果
- `export`：导出到 `exports/`

因此这个页面本质上是：

`case-organizer 的本地图形化入口层`

不是独立新系统。

## 10. 首版范围

首版需要做：

1. 单页六步向导
2. 病例目录初始化
3. 分类目录可视化
4. 本地上传到指定分类目录
5. 处理进度展示
6. 候选结果轻量校对
7. 导出完成页

首版不做：

1. 复杂多人协作
2. 云端同步
3. 医学分析建议
4. 复杂富文本编辑器
5. 高级批量规则配置

## 11. 下一步实现建议

推荐实现顺序：

1. 先做静态向导页和流程骨架
2. 再接 `init` 和 `scan`
3. 再接 `review`
4. 最后接 `export`

推荐技术方向：

- 本地 Web 前端
- 与 `case-organizer` Python 项目同仓或同子项目维护
- 风格与 `ca199_toolbox` 统一

## 12. 结论

`case-organizer` 应增加一个面向患者的单页向导式 HTML/Web 入口。

它不是替代 `ca199_toolbox`，而是负责把“建立病例目录、放资料、自动整理、人工校对、导出结果”这条路径做成普通患者可使用的产品流程。

它与 `ca199_toolbox` 保持统一设计体系，但承担不同任务：

- `case-organizer` 负责整理入口
- `ca199_toolbox` 负责病情展示
